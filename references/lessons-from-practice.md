## 一、方案设计（阶段2 引用）

### 教训1：新功能不动旧契约

**结论**：增量功能的第一设计原则是保持既有输出契约不变，让所有下游零改动。

**来源案例**：深度审稿模式内部有 8 次独立的 LLM 调用，但最终汇总报告刻意沿用原有的七部分报告结构——结果页的录用建议判词解析、localStorage 历史、追问上下文、Markdown 导出**全部零改动兼容**。改动契约的成本等于所有下游适配的成本之和，而且下游往往藏在看不见的地方（判词解析就是个例子）。

**应用方法**：PRD 评审增加固定检查项——"这个功能改变了哪些既有输出/接口？每个改变列举下游受影响方"。能不变的不变；必须变的，列出完整迁移清单并单独评审。

### 教训2：现实约束撑不起设计时，降级并显式声明

**结论**：环境约束撑不起理想设计时，选择降级能力并在产品里显式声明局限，而不是硬塞、也不是假装能做。

**来源案例**：参考的审稿 skill 里表格核查依赖 .tex 表格源文件，而网页端只有 PDF 提取文本（表格数字会失真）。处理：该代理降级为"基于可辨认文本核查注释完整性与交叉引用"，并要求对无法判断的项目输出 `[无法核实]` 标注而非武断判定。

**应用方法**：PRD 中每个功能标注"依赖的输入质量"；输入达不到时功能的行为（降级/报错/标注）必须写进边界条件，不允许留白让实现时随机发挥。

### 教训3：AI 产品的输出质量靠接地规则，不靠口头期望

**结论**：凡含 AI 生成内容的功能，提示词里必须有显式接地（grounding）规则：不虚构引用、无法核实显式标注、强断言转人工确认。

**来源案例**：贡献辩护/怀疑两个代理的接地规则——文献比较限于论文自身参考文献，超出部分标 `[UNVERIFIED-需作者确认]`，绝不虚构作者/年份/发现。这条规则直接决定了产品的可信度下限。

**应用方法**：所有生成类功能的验收标准必须包含"幻觉防护"条目：什么不允许编造、不确定时输出什么标记、哪些断言必须转人工。

## 二、工程执行（阶段5 引用）

### 教训4：长链路编排，串行+单步容错先于并行+速度

**结论**：多步骤（多Agent/多次调用）流程，先用串行+逐步容错跑通，再谈并行优化。限流友好、失败可定位、进度可展示，比墙钟时间重要。

**来源案例**：深度模式的 7 个专项代理串行执行，单个失败留占位继续——故障注入实测：第 3 个代理网络中断，流程照样走完 8 步，汇总报告仍产出。用户看到的是"1 个代理失败"而不是"全部白跑"。

**应用方法**：技术方案评审必问——"第 k 步失败，整个流程的行为是什么？"答不上来就是没设计完。

### 教训5：无外部依赖的验收测试

**结论**：用桩（stub）把编排逻辑与外部服务解耦，没有 API key、没有真实环境也能验证流程正确性；故障注入是必修项。

**来源案例**：深度模式上线前，用 DOM+fetch 桩在 Node 里跑通 22 项断言（调用次数与顺序、参数注入、历史存储、UI 渲染、上下文建立）+ 1 项中途失败容错测试。真实 API 验收因无 key 推迟，但流程正确性已提前锁定，上线后一次通过。

**应用方法**：验收标准区分"流程正确性"（可离线测，先行完成）与"真实效果"（需在线测，资源到位后补）。

### 教训6：昂贵操作必须成本透明

**结论**：耗时/耗 token 的操作要在用户触发前明示量级，让用户知情选择。

**来源案例**：深度模式在 UI 上标注"约 10-15 分钟"，与快速模式并列供用户自行取舍；未标预期的"免费"感会直接转化为"卡死了"的差评。

**应用方法**：PRD 每个功能标注预期耗时/成本档位；超过阈值（如 5 分钟）必须在交互上体现，并提供更便宜的替代路径。

## 三、上线与变更（阶段4/5 引用）

### 教训7：部署验证三步闭环，网络抖动先重试再下结论

**结论**：上线验证 = 合并状态 -> 构建状态 -> 线上内容抽查，三步缺一不可；瞬时网络失败先重试，不要当结论。

**来源案例**：深度模式上线时 Pages 构建显示成功，但第一次 curl 线上页面超时且内容为空——重试后 HTTP 200、新功能元素全部就位。若当时下"部署失败"的结论就是误判，会触发无意义的回滚。

**应用方法**：上线 checklist 固化三步；任一步验证失败先重试 1-2 次，仍失败再进入排查。

### 教训8：外向/不可逆操作：预检副作用 -> 确认 -> 告知恢复路径

**结论**：影响外部或难以回退的操作（覆盖、删除、改可见性、发布），执行前做三件事：查副作用、获用户确认、备好恢复路径说明。

**来源案例**：三个真实场景——安装 skill 遇同名冲突时不覆盖而是问用户（最终改名安装）；推送 GitHub 等用户明示；仓库转私有前先查 Pages 副作用（免费账号私有仓库不能用 Pages，站点会下线），执行后同步给出恢复命令。

**应用方法**：总监终审对"变更类"需求的裁决必须附带副作用清单与回滚方案，缺一不批。

### 教训9：环境资产要有迁移预案，重复文件是事故痕迹

**结论**：磁盘/机器迁移会造成丢 git 历史与成堆的"(1)"重复文件，事故痕迹会长期潜伏。

**来源案例**：paper-reviewer-web 曾因磁盘迁移丢失 .git、积累 41 个重复文件，直到专门收口才清理并接回远端历史；同样的"(1)"成对模式至今还留在本地 pm-team 工作区的 skills/ 目录里。

**应用方法**：阶段5结束时检查工作区是否出现重复文件模式；重要资产必须 git 管理，无 git 的目录按高风险资产对待，优先补 git。

## 四、协作与知识管理（全流程引用）

### 教训10：同一个错误犯两次以上，改方法而不是更小心

**结论**：重复失误说明是流程/工具缺陷。解法是换成无状态、防错的执行方式，从机制上消除犯错可能——"下次注意"不算对策。

**来源案例**：实际执行中曾连续 4 次犯同一错误——命令漏切工作目录，每次都"无害失败"但浪费轮次。最终解法不是自我提醒，而是全部改用带路径参数的无状态命令形式（`git -C <path>`、`uv --directory <path>`），错误从此不可能发生。

**应用方法**：复盘时把"人/Agent 失误"归类为流程缺陷而非态度问题；对策必须是结构性的（换工具/换形式/加检查点），在复盘报告里禁止出现"加强注意"类对策。

### 教训11：决策留痕要带 Why 和 How to apply

**结论**：只记"做了什么"的日志没有复用价值；决策记录必须含背景理由和下次怎么用。

**来源案例**：跨会话记忆采用"结论 + Why + How to apply"结构。例如 Python 版本坑的记录：venv 必须用 3.13（Why：3.14 下 tiktoken 没有预编译 wheel，会因缺 Rust 编译器构建失败；3.13 有现成 wheel）；重建环境直接 `uv sync --python 3.13`（How to apply）。下次遇到直接执行，不重新踩坑。

**应用方法**：决策日志模板强制三字段：决策内容 / 理由（Why）/ 下次如何应用（How to apply）。

### 教训12：开源资产跨运行时复用，归属要留

**结论**：提示词编排资产（如开源 skill）本质是与运行时无关的方法论，可以移植到其他平台（Claude Code skill -> Web 产品），保留许可归属即可。

**来源案例**：深度多代理模式的 7 个代理提示词移植自 claesbackman/AI-research-feedback（MIT），翻译并适配中文论文场景；归属在代码头部注释与 README 双处标注。"先找资产再自研"这一条直接省掉了一周的提示词设计。

**应用方法**：方案调研阶段先搜现成资产（许可证友好优先）；自研前列出"移植改造点"清单——通常远短于从零开发的清单。
